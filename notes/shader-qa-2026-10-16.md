# Shader QA and speed pass (2026-10-16)

Scope: every shader RT64 builds for this port (lib/rt64/src/shaders, patched by lib-patches/rt64.patch): the game's own 24 files and upstream RT64's. Build 36f7460 on main (rebased from e91950c), Linux container, dxc-linux 1.8 (Windows ships dxc 1.7).

## 1. Compile check

Every shader the build compiles was compiled here with the build's own dxc flags, both ways:
81 variants as SPIR-V (what the Linux build makes) and as DXIL (what L's Windows build makes), plus the 3 DXIL-only
library builds (RasterPSLibrary, RasterPSLibraryMS, RasterVSLibrary) that the Windows runtime links each specialised
shader against. Result: 165 of 165 compile, no errors, no warnings.
(The spec-constant variants of RasterPS/VS do warn as DXIL, "Initializer of external global will be ignored", but no
build makes those as DXIL; they are SPIR-V and Metal only.)

Script: tools are not committed; the commands are the `dxc-linux` lines in build-cmake/build.ninja.

## 2. Findings from reading the shaders

### A. Vulkan start-up: "Sorting shader failed, possibly due to a cyclic dependency" (4 times). Harmless, but noise.
RT64 specialises the raster pixel shader on Vulkan with re-spirv (a SPIR-V optimiser in lib/rt64/src/contrib). Its
topological sort cannot cope with loops, and the 3D grass shells code (Grass.hlsli, GrassShell: the trail loop and the
4-cell x 5-blade loops) is the only looping code in RasterPS, so the sort fails for all four pixel shader variants.
The game carries on with the partial order. Measured with re-spirv's own CLI on the built shader: the specialised
shader that comes out is 6548 instructions, the same as with a fixed sort, so nothing is lost. A debug build would
hit the assert in rt64_raster_shader.cpp. A small re-spirv patch (leave loop back-edges out of its graph, treat the
loop's merge value as a variable) makes the sort succeed and keeps the output identical; it is a change to a
third-party library for no speed gain, so it is left for L's decision.

### B. Every game draw's pixel shader carries all the port's effect code. L's decision.
The specialised raster pixel shader (one per game material) is 6548 instructions here against 1880 for the same
material in upstream RT64: 3D grass shells and blades, deep snow, Banjo's fur, Kazooie's feathers, night-time lamps
and the water mask all sit behind push-constant branches in the one shader. Branches on a push constant are skipped
cheaply, but the GPU still has to reserve registers for the worst path, which lowers how many pixels run at once for
every ordinary draw (floors, walls, Banjo). Lavapipe can't measure that. The fix would be a second, lean build of the
raster shaders for ordinary draws (the effects draws already use their own pipelines on the blades path). Medium job;
needs L's decision, and a before/after on L's PC is the only real test.

### C. Depth of field reads the focus box 25 times a pixel. L's decision.
SceneEffectsPS DepthOfField (and PhotoGradePS's copy) finds the focus by reading the depth at 25 points round the
middle of the picture, in every pixel, every frame, for a value that is the same for the whole frame. A one-pixel
pass could compute it once (as the eye-adaptation passes already do) and the main pass read it. No visible change.
Only costs with Depth of Field on (off in every preset).

### D. Fireflies: 162 firefly positions worked out again in every pixel. L's decision.
DayFireflies loops over 9 x 9 cells x 2 fireflies and for each works out its hashes, its looping path, its
projection to the screen and whether it is hidden, all of which are the same for every pixel; only the last distance
test depends on the pixel. At 1440p that is about 600 million firefly evaluations a frame at night. Either a small
pre-pass that writes the 162 screen positions to a buffer (no visible change), or drawing the fireflies into the
quarter-size bloom texture (they are added as glow anyway; slightly softer cores). Only costs at night with Fireflies
on.

### E. Bounce light takes 60 texture reads a pixel. L's decision.
BounceLight reads 12 depths and 4 bilinear colour samples per depth (48 colour reads). A half-size blurred copy of
the scene would give the same averaged colour from 12 reads, with a slightly different (smoother) result. Only
costs with Bounce light on (off in every preset).

### F. The output pass raises every pixel to the brightness gamma even at 1.0. Small; L's decision.
VideoInterfacePS runs pow(colour, gamma) for the whole window every frame. Skipping it at gamma 1.0 saves three
pow operations a pixel; pow(x, 1) is x to within a rounding error, so in theory not bit-exact, in practice no pixel
changes. Not done, as it is "a visible result" by the letter of the brief.

### G. Things that look odd on a read but are fine
- RasterPS.hlsl: `const uint nativeSampler = renderFlagNativeSampler1(rp.flags);` is unused (upstream code).
- BloomPS, PhotoGradePS, SmaaPS, FxaaPS, FsrPS declare gTexture2 and never use it (harmless).
- GrassGS emits furAnchor for every blade vertex; only pixelated blades read it (the vertex layout is shared with
  RasterVS, so it must be there).
- Texture reads inside loops, by design of the effect: sun shadows 24 steps, ambient occlusion 8, water reflection up
  to 32, light shafts 24, depth of field 24 (x2), FXAA up to 48, the bloom brightness pass 256 (one pixel). Branches on
  per-pixel values are everywhere in SceneEffectsPS and are what the effects need; none look wrong.
- GrassGS: every pass runs all 32 invocations of every ground triangle again and most exit at once; inherent to how
  the passes are counted (the draw's largest triangle).

## 3. Speed changes made (one commit each, no visible change)

| Commit | Change | Shader instructions (SPIR-V / DXIL) |
|---|---|---|
| 0ed446c | 3D grass blades and feathers skip the shell world position's screen derivatives (feathers skip the position too) | RasterPS: branches only; saves ~30 ALU + 6 derivative ops per blade pixel |
| 84c0736 | GrassGS checks a blade's next detail level in one step instead of walking all levels again | GrassGS: up to 8 hashes fewer per blade |
| 0afdf78 | Water mask read once where either kind of water counts (steepness, waterfalls: 5 to 10 reads a pixel) | SceneEffectsPS 23468 -> (see below) |
| 95f0c70 | Ambient occlusion and sun shadows share one surface normal (4 depth reads + the normal, once instead of twice) | SceneEffectsPS -> 21262 / 21861 (from 23468 / 22850, -9% / -4%) |

Why they cannot change the picture: each removes a computation whose result was either unused on that path
(derivatives for blades), recomputed from identical inputs (the normal, the detail-level walk), or read twice from the
same texel (the water mask; flat water has alpha 1 and a steep draw a quarter, so one read decides both).

## 4. Measurements (headless, lavapipe software Vulkan, Original resolution, no MSAA, Enhanced preset + 3D grass 50 +
Deep snow + Banjo fur 50)

Median GPU ms per game frame once shaders had compiled (about 37 samples a run), two rounds each:

| Run | Spiral Mountain total | effects pass | Icy Side total | effects pass |
|---|---|---|---|---|
| before, round 1 | 89.4 | 23.4 | 77.1 | 30.2 |
| after, round 1 | 85.3 | 22.9 | 77.1 | 31.1 |
| before, round 2 | 87.3 | 23.4 | 79.5 | 32.0 |
| after, round 2 | 92.1 | 24.2 | 76.6 | 30.3 |

The differences are inside the run-to-run noise, so headless shows no measurable change either way; the gains are
small relative to what a software renderer spends on everything else, and only L's GPU can show them. What the
numbers do confirm is that nothing got slower.

Screenshots at 70 s and 80 s into each run: before vs after differ in 0.4 to 1.8% of pixels (grass sway and
animation frames), the same as before-vs-before (0.3 to 1.3%). Side by side (before left, after right):
[before-after.png](screens/shader-qa/before-after.png).

Lavapipe runs shaders on the CPU, so these numbers say "less work", not what L's GPU will save. Run-to-run noise is
about +-10%, and the first 40 s of a run are skewed by shader compiling.

What L's GPU should show: B is the one that can be felt everywhere if the GPU was short of registers for the
big shader; D makes night with fireflies clearly cheaper at high resolutions; C and E only count with their
settings on; A and F change no speed anyone will see. If anything looks different, each change is its own
commit to revert; B and A go together (reverting B alone is fine, reverting A alone breaks B on Vulkan).

Lesson for other threads: ninja re-runs cmake whenever a CMakeLists.txt changed (lib/rt64's included), and
that configure resets lib/rt64 to the committed patch. Regenerate lib-patches/rt64.patch before every build.
